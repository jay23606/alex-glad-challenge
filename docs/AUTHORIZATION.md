# Авторизация в web/ — как устроено

Источник фактов: `docs/advanced-day-02/research-run-01.md` (прогон профиля Research,
2026-10-23). Документ описывает текущее поведение, ничего не меняет.

## Механизм

Stateless HMAC-cookie сессия одного администратора, без серверного хранилища сессий:

```
admin_session = `${exp}.${hex(HMAC-SHA256(WEB_AUTH_SECRET, "admin:" + exp))}`
```

- Формат и проверки: `web/lib/auth.ts:20,50-56,58-72` (16 цифр exp, пересчёт HMAC,
  сравнение через timingSafeEqual по sha256-дайджестам). TTL 7 дней (`SESSION_MAX_AGE_S`).
- Пароль: `WEB_ADMIN_PASSWORD`, сравнение timing-safe (`web/lib/auth.ts:42-48`).
- Секреты читаются только в `web/lib/auth.ts` через `loadEnvUpward()`
  (`challenge/src/core/env.ts:12-27`); наружу — только Boolean-флаги
  (`isAdminAuthConfigured`, `web/lib/auth.ts:29-34`), значения не покидают модуль.

## Два слоя проверки

1. **Middleware-гейт** — `web/middleware.ts:83-101` (runtime nodejs): cookie
   проверяется на каждом запросе, кроме точного allowlist `PUBLIC_PATHS`
   (`web/middleware.ts:30-53`, exact match pathname, без префиксов).
   Неавторизованным: страницы → `302 /login?next=<pathname>` (query отбрасывается),
   `/api/*` → `401 JSON`. Fail-closed: без `WEB_AUTH_SECRET` валидных сессий не бывает.
2. **Второй слой `requireAuth(req)`** — в роутах с внешними эффектами:
   `blog/digest/generate`, `blog/posts/[id]/publish`, `blogs/[slug]`, `rag/index-tg`,
   `rag/notes` (POST/DELETE/GET), `summary`, `telegram/publish`, `tg/collect`,
   `rag/index` (унифицировано 2026-10-23, issue #25). Защита от пропуска middleware
   (например, edge-кейс деплоя).

Для Server Components — `web/lib/server/session.ts` (`isAdminAuthed()` через `cookies()`).

## Мобильный вход / Bearer-сессия

- `POST /api/mobile/login` — публичный path (точное совпадение в `PUBLIC_PATHS`).
  Принимает `{password}`, проверяет `WEB_ADMIN_PASSWORD` и возвращает тот же
  `createSessionValue()` в теле как `token` (TTL 7 дней, **без** Set-Cookie),
  `Cache-Control: no-store`; ошибки — `{ok:false,error}`.
- Android шлёт `Authorization: Bearer <token>`. `isMobileAuthed`
  (`web/lib/auth.ts:100-107`) принимает подписанную session-строку **или**
  статический `MOBILE_API_TOKEN` (остаётся для автоматизации). Bearer действует
  только на `/api/*` через middleware (`web/middleware.ts:86-87`), страницы он
  не открывает; `requireAuth`-роуты (cookie-only: summary, rag/*, blog
  digest/publish, telegram/publish, tg/collect) Bearer не принимают.
- Rate-limit общий с `/api/auth/login` — `web/lib/server/loginRateLimit.ts`
  (10 неудач / 15 мин, глобальное окно; успех сбрасывает окно).
- Отзыва токена нет: он живёт до `exp`; инвалидация — только смена
  `WEB_AUTH_SECRET`. «Выход» в Android удаляет токен только на устройстве.

## Компромиссы (осознанные)

- Отзыва сессий нет: украденная cookie (и выданный мобильный Bearer) живёт до
  `exp`; единственная инвалидация — смена `WEB_AUTH_SECRET`. Мобильный «выход» —
  только удаление токена на устройстве.
- Cookie без `secure` и без `__Host-`-префикса; CSRF — `sameSite=lax`, отдельных
  токенов нет; logout — POST (`web/app/api/auth/logout/route.ts:1-3`).
- Rate-limit логина глобальный (10 неудач/15 мин), не per-IP — сознательно
  (`web/lib/server/loginRateLimit.ts:1-33`): 10 неверных попыток блокируют
  вход владельцу, рестарт процесса сбрасывает счётчик. Окно общее для
  cookie-входа и мобильного `/api/mobile/login`.

## Inbound webhooks (публичный приём, HMAC вместо сессии)

`POST /api/integrations/inbound/[id]` — публичный эндпоинт, мутирующий данные
по HMAC-подписи вместо сессии: путь открыт в middleware (как и auth/demo/style-пути),
аутентификация — hex HMAC-SHA256 подпись сырого тела в `x-artel-signature`
(`web/app/api/integrations/inbound/[id]/route.ts`,
`verifySignature` в `challenge/src/core/webhooks.ts`).

**Секрет хука хранится в SQLite открытым текстом** — осознанный компромисс, как у
всех webhook-провайдеров (GitHub, Stripe): HMAC-верификация требует пересчёта
подписи тем же секретом, хеширование (даже с солью/KDF) сломало бы проверку.
Митигируется окружением: локальная loopback-БД, каталог `.data/` вне git, секрет
показывается один раз при создании хука, `GET` списка секретов не возвращает
(`web/app/api/integrations/inbound/route.ts`). Секреты не логируются и не эхоятся.

**Злоупотребление публичным путём ограничено двухуровневым rate-limit'ом**
(issues #62, #103): in-memory fixed-window, окно 5 минут, состояние в `globalThis`,
глобальный, не per-IP (XFF за прокси подделываем), сбрасывается рестартом:

- **per-hook бюджет** — 30 неудач конкретного hookId (401/400, и 404 несуществующего
  id) → `429` + `Retry-After` до конца окна. Бюджеты изолированы: перебор против
  одного хука не блокирует остальные. Успешная подпись (доказательство владения
  секретом) сбрасывает бюджет только своего хука (паттерн логина).
- **глобальный abuse-guard** — 200 неудач на процесс, скоуп — только перебор id:
  невалидный id (гейт до чтения тела) и неизвестный хук (после `getHook`).
  Неудачи известного хука глобальный счётчик не наполняют и им не блокируются —
  мусор по чужим id не отзывается `429` на легитимные подписанные доставки.
- карта per-hook бюджетов капится 1000 записями: истёкшие окна вычищаются; если все
  живы — новый id остаётся без учёта (skip tracking), чужие бюджеты не вытесняются.
  Предусловие skip-tracking практически недостижимо: нужны ~1000 живых бюджетов за
  одно окно, а перебор id раньше закрывается глобальным капом 200.

**Accepted risk F2 (issue #103):** адресный lockout конкретного хука — 30 мусорных
подписей за 5 мин отгоняют легитимные доставки этого хука в `429` до конца окна.
Это цена любого per-key rate-limit (без per-key гейта подбор подписи не ограничить);
остальные хуки продолжают принимать. Митигации: мониторинг `429` на inbound-пути,
ротация/удаление хука (`DELETE` под session-auth), окно отпускает само через ≤5 мин.

**Replay-защита (issue #97, accepted risk + опциональное ослабление):** подпись
покрывает только тело — перехваченную валидную доставку можно повторить, дедупа
по id события нет. Для текущей модели угроз повтор принят как осознанный риск:
отправители — внутренние сервисы и ручной `curl`, web слушает только loopback
`127.0.0.1`, перехват трафика на loopback требует уже локальной компрометации,
при которой под угрозой и секрет хука, и вся машина; перебор подписи ограничен
rate-limit'ами (см. выше). Ослабление без ломки отправителей — опциональный
заголовок `x-artel-timestamp` (Unix ms): нет заголовка — прежнее поведение
(контракт подписи не менялся); есть — запрос принимается только при
`|now − ts| ≤ 300 с`, иначе `400` «stale/invalid timestamp». Заголовок в подпись
НЕ входит (контракт заморожен), поэтому повторщик может его подменить или просто
снять — без заголовка проверки нет вовсе; осознанно: защита адресована наивному
повтору захваченных байт целиком (ретрай, переигрывание из очереди/лога), где
заголовок остаётся с исходным ts, а не активному MITM — для loopback-модели
угроз достаточно. Рассинхрон часов отправителя больше ±300 с даёт `400` на
каждую доставку и выжигает per-hook бюджет: после 30 фейлов хук уходит в `429`
до конца окна — синхронизировать часы и мониторить `429` на inbound-пути.
Отправитель, которому важна
защита от повтора, ставит заголовок один раз при отправке (`Date.now()`).
При выносе inbound-путей за loopback этого недостаточно — нужен настоящий
анти-replay: nonce с серверным хранилищем (дедуп) или подпись заголовков
(новый контракт подписи, отдельное решение с миграцией отправителей).

**Oracle 404-vs-401 (решение по #92, поведение не менять):** неизвестный id →
`404 «hook not found»`, известный id с неверной подписью → `401 «invalid
signature»`. Различение сознательное — легитимный интегратор отличает опечатку
в URL от ротированного секрета. Цена: существование id перебирается по статусу.
Утечка осознанная: существование id не секрет (id — маленькие последовательные
целые, настоящая граница доступа — секрет хука, не угадывание id), а схлопывание
404→401 устранило бы oracle, но ухудшило бы диагностику. Лимиты ограничивают
скорость перебора, не устраняя утечку: глобальный guard — 200 id за 5-минутное
окно (для малых последовательных id этого достаточно), а per-hook бюджет 30/5 мин
ключуется самим id и на перебор чужих id не влияет (решение продублировано
комментарием в `web/app/api/integrations/inbound/[id]/route.ts`, ветка
`if (!hook)`).

Рекомендации владельцу:

- не переиспользовать секреты из других систем — генерировать хук через UI/API;
- отправителям, которым важна защита от повтора доставки, — передавать
  `x-artel-timestamp` (Unix ms, окно ±300 с; проверка в
  `web/app/api/integrations/inbound/[id]/route.ts`);
- ротация = удаление хука + создание нового (`DELETE` под session-auth, нового
  секрета нет по умолчанию);
- неиспользуемые хуки удалять: каждый живой хук — действующий публичный путь;
- при подозрении на утечку секрета — немедленно удалить хук (старые подписи
  перестают приниматься сразу).

Проверка: unit `web/test/unit/inbound-webhooks-route.spec.ts` (в т.ч. describe
«rate-limit POST …»: 30 неудач хука → 429 у него при рабочем соседнем хуке,
200 переборных id → 429 перебору при проходящей доставке в известный хук,
окно истекло → снова 401, успех сбрасывает бюджет своего хука; describe
«…x-artel-timestamp — replay-защита (#97)»: без заголовка прежнее поведение,
свежий ts → 200, протухший/из будущего/мусорный → 400 без мутации, невалидная
подпись + мусорный ts → 401 (timestamp не oracle), массовый повтор → 429).

## Открытые вопросы (решение за владельцем)

1. Нужен ли отзыв сессий (version/epoch в секрете или server-side реестр)?
2. Ставить ли `secure`/`__Host-` — зависит от гарантий reverse-proxy (TLS терминируется
   снаружи, конфиг в репозитории отсутствует).
3. Минимальная длина `WEB_ADMIN_PASSWORD` (сейчас — только непустота,
   `web/lib/shared/forms.ts:327-330`).
4. Глобальный rate-limit: блокировка владельца 10 запросами — приемлемо?
5. Шапка-комментарий middleware актуализирована (#24); держать синхронным.
