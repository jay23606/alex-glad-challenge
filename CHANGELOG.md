## День 18 — MCP-инструмент с фоновым выполнением и Telegram-напоминаниями
**Дата:** 2026-06-27
**Ветка:** `day-18`

**Задание (полный текст):**
> Создать MCP-инструмент с отложенным фоновым/периодическим выполнением,
> который работает 24/7. Реализовать TODO-планировщик с напоминаниями
> в Telegram: задачи с настраиваемым интервалом повторения (ежечасно,
> ежедневно, еженедельно).

**Сделано:**
- MCP HTTP-сервер (`day-18-server.ts`) с 8 тулзами:
  `add_todo`, `list_todos`, `complete_todo`, `dismiss_todo`, `delete_todo`,
  `send_summary`, `call_remote_tool`, `list_remote_tools`.
- SQLite-хранилище тудушек (`TodoDb`) с поддержкой recurring:
  `daily` (раз в день), `weekly` (день недели), `hourly` (каждые N часов).
- Фоновый цикл: каждые 60с проверяет due-задачи и отправляет в Telegram.
- **Регулярный ежедневный summary** (`runDailySummary`): фоновый таймер каждые
  5 мин проверяет — если локальный час ≥ `SUMMARY_HOUR` (по умолчанию 9) и сегодня
  сводка ещё не отправлялась (дата в `todo_meta.last_daily_summary_date`), шлёт
  список всех pending-задач в Telegram одним сообщением. Guard по дате убирает
  дубль в тот же день; пустой список не отправляется. Заменил старый «spam-loop»
  (отправка due-задач каждые 60с), который мешал жить.
- Telegram-отправка через HTTP-прокси (gost → socks5) + `undici.ProxyAgent`.
- Systemd-сервисы на VPS: `mcp-server` (scheduler) + `gost-proxy` (HTTP↔socks5).
- MCP endpoint доступен через Caddy: `https://api.memo7.ru/mcp`.

**Параметры:**
- Провайдер: Telegram Bot API через HTTP-прокси (GOST).
- База: `challenge/.data/todos.sqlite`.
- Прокси: `gost -L http://127.0.0.1:3128 -F socks5://...` (systemd `gost-proxy`).
- Интервал: проверка daily-summary каждые 5 мин, реальная отправка — раз в день
  после `SUMMARY_HOUR` (по умолчанию 9). `SUMMARY_HOUR` задаётся в `.env` (0–23).

**Архитектура:**
```
Компьютер (curl) ──→ VPS: Caddy :443 → MCP :3001
                                       │
                                       ├── SQLite (todos.sqlite)
                                       ├── daily-summary таймер (5 мин → раз в день)
                                       └── Telegram Bot API
                                            └── gost :3128 → socks5 → api.telegram.org
```

**Примеры использования (curl с компьютера):**
```powershell
# Добавить напоминание каждые 2 часа
curl https://api.memo7.ru/mcp -X POST -H "Content-Type: application/json" `
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"add_todo","arguments":{"text":"Проверить почту","recurring":"hourly","interval_hours":2}}}'

# Ежедневная задача
curl https://api.memo7.ru/mcp -X POST -H "Content-Type: application/json" `
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"add_todo","arguments":{"text":"Сделать зарядку","recurring":"daily"}}}'

# Посмотреть все задачи
curl https://api.memo7.ru/mcp -X POST -H "Content-Type: application/json" `
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_todos","arguments":{}}}'

# Отправить сводку вручную
curl https://api.memo7.ru/mcp -X POST -H "Content-Type: application/json" `
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"send_summary","arguments":{}}}'
```

**Выводы:**
- socks5-туннель напрямую (SocksClient + TLS) работал в изоляции но завис в tsx+systemd —
  не удалось найти причину, переключился на gost HTTP-прокси.
- undici 8.x несовместим с Node 22 встроенным fetch (invalid onRequestStart) —
  нужен undici 7.x.
- `Connection: close` + Content-Length парсинг — обязательны для raw HTTP поверх TLS,
  иначе `end` event не приходит.
- MCP JSON-RPC протокол — простой и рабочий способ дать CLI-доступ к серверным
  тулзам без отдельного SDK.

**Код:**
- `challenge/src/core/todoDb.ts` — SQLite БД тудушек.
- `challenge/src/core/agents/telegram.ts` — отправка в Telegram.
- `challenge/src/demos/day-18-server.ts` — MCP HTTP-сервер с 8 тулзами.
- `challenge/src/demos/day-18.ts` — оригинальный день 18 (демо).
- Команда: `pnpm --filter challenge start -- scheduler`

## День 19 — Композиция MCP-инструментов
**Дата:** 2026-06-27
**Ветка:** `day-19`

**Задание (полный текст):**
> Создайте несколько MCP-инструментов, например: `search`, `summarize`, `saveToFile`.
> Реализуйте пайплайн: первый инструмент получает данные, второй обрабатывает,
> третий сохраняет результат. Проверьте: автоматическое выполнение цепочки и
> корректность передачи данных между инструментами.
> Результат — автоматический пайплайн из нескольких MCP-инструментов.
> Формат — видео + код.

**Продукт (по задумке автора челленджа):** юзер пишет запрос в REPL/CLI
(например: «просканируй последние 200 сообщений в чате "факты в чате" и пришли
отчёт») — после этого агент сам гонит цепочку MCP-тулов. Это НЕ демка с
авто-прогоном: триггер всегда юзер, агент действует по его запросу. Bot API не
умеет читать историю — для скана чата нужен MTProto userbot (api_id/api_hash/session).

**Сделано:**
- 3 инструмента добавлены на ЕДИНЫЙ работающий сервер (`day-18-server.ts` =
  api.memo7.ru), а не отдельный день-сервер и не демка:
  `scan_chat_messages` (MTProto, получить) → `analyze_messages` (детерминированный
  отчёт по авторам/терминам/ссылкам, без LLM) → `send_to_chat` (отправить отчёт в
  `TG_CHAT_ID` через Bot API).
- `core/agents/telegramScan.ts` — MTProto-клиент (GramJS, StringSession из env):
  connect/disconnect, `scanChatMessages(chat, limit)` (по @username / id /
  заголовку диалога), `analyzeMessages` — чистая функция.
- Точка входа для юзера — команда `agent` в CLI и `/agent` в REPL, общая через
  `runAgentRequest` (`core/mcpAgentLoop.ts`). Цепочку вызывает сама LLM в цикле
  `CALL/RESULT`; данные протекают через кеш последнего скана и контекст модели.
- `runAgentLoop` вынесен из `day-17.ts` в `core/mcpAgentLoop.ts` (+ `runAgentRequest`,
  `DEFAULT_AGENT_SYSTEM`), переиспользуется day-17 и `/agent`.

**Параметры:**
- MTProto (скан истории): `TG_API_ID`, `TG_API_HASH`, `TG_SESSION` (userbot).
- Доставка отчёта: `TG_BOT_TOKEN`, `TG_CHAT_ID`, `HTTPS_PROXY` (Bot API, как day-18).

**Выводы:**
- Композиция тулзов — это агентский цикл: LLM сама решает порядок, сервер даёт
  детерминированные шаги. Поэтому отдельной «демки дня» нет — вход даёт юзер.
- Чтение истории Telegram — только MTProto; Bot API годится лишь для отправки.
- «Обработка» (analyze) сделана чистой функцией без LLM — сервер не зависит от
  модели; 200 сообщений идут в серверный кеш, а не в контекст LLM.

**Код:**
- `challenge/src/core/agents/telegramScan.ts` — MTProto-сканер + анализ.
- `challenge/src/core/mcpAgentLoop.ts` — цикл tool-calling + `runAgentRequest`.
- `challenge/src/demos/day-18-server.ts` — +3 тула скан-пайплайна на живом сервере.
- Команды: `pnpm --filter challenge start -- agent "<запрос>"`, в REPL — `/agent <запрос>`.

## День 20 — Orchestration MCP: «Брифинг дня»
**Дата:** 2026-06-28
**Ветка:** `day-20`

**Задание (полный текст):**
> Зарегистрируйте несколько MCP-серверов. Сделайте, чтобы:
> - агент выбирал нужный инструмент;
> - корректно маршрутизировал запросы;
> - выполнял длинный флоу взаимодействия.
> Проверьте:
> - сценарий с инструментами с РАЗНЫХ серверов;
> - корректность выбора и порядка вызовов.
> Результат: длинный флоу с несколькими MCP-серверами и инструментами.

**Продукт:** «Брифинг дня» для тимлида-отца-фаната. Триггер — юзер (команда
`day-20`); агент сам собирает сводку: дата + заметки из Obsidian-vault
(+ опционально web) → записывает заметку «Брифинг <дата>» обратно в vault.

**Сделано:**
- Два MCP-сервера в одном персистентном процессе (`day-20-server.ts`, деплоится
  как сервис — не демка и не in-process mock):
  - `obsidian-mcp` :3020 — `read_note` / `search_notes` / `create_note` над vault
    (`.data/vault/*.md`, filesystem, без плагина Obsidian и без Local REST API);
  - `world-mcp` :3021 — `get_current_time` (часы сервера) + `fetch_url` (web).
- `core/mcpOrchestrator.ts` — кросс-серверный роутер: подключается к N серверам,
  мержит их инструменты в один список, каждый `CALL` адресует на сервер-владелец.
  Обобщение односерверного `mcpAgentLoop`; на cap-hit делает forced final summary,
  иначе «ответом» остался бы сырой CALL последней итерации.
- `demos/day-20.ts` — тонкий клиент (как `day-18.ts`): коннект к обоим серверам,
  агентский цикл, trace маршрутизации. URL'ы через env `OBSIDIAN_MCP_URL` / `WORLD_MCP_URL`.
- CLI: `day-20-server` (поднять серверы), `seed-vault` (опциональные примеры заметок).
- Текстовый протокол `CALL/RESULT` (как day-17/19) — надёжнее нативного tools-API.

**Параметры:**
- LLM: `DEEPSEEK_API_KEY` / `OPENROUTER_API_KEY` (как везде).
- Серверы: `OBSIDIAN_MCP_URL` (по умолч. `http://localhost:3020/mcp`),
  `WORLD_MCP_URL` (`http://localhost:3021/mcp`); порты — `--obsidian-port` / `--world-port`.
- Vault: `OBSIDIAN_VAULT_DIR` (по умолч. `.data/vault`).

**Выводы:**
- Кросс-серверная оркестрация = агентский цикл над объединённым списком тулзов:
  шаг N на сервере A, шаг N+1 на сервере B — порядок выбирает модель, адрес — роутер.
  Замер прогона: `get_current_time` (world) → `read_note`/`search_notes` (obsidian)
  → `create_note` (obsidian).
- Obsidian как домен = filesystem-MCP над `.md`, без плагина/REST API — vault это
  просто папка.
- Промпт НЕ должен bait'ить ненадёжный web (Google JS-gate выдаёт бесполезный HTML),
  если данные уже есть в vault — иначе агент зацикливается на `fetch_url`.

**Код:**
- `challenge/src/core/mcpOrchestrator.ts` — мульти-серверный роутер.
- `challenge/src/demos/day-20-server.ts` — персистентный процесс (2 MCP-сервера).
- `challenge/src/demos/day-20-obsidian-server.ts` — vault MCP + сид.
- `challenge/src/demos/day-20-world-server.ts` — time + fetch MCP.
- `challenge/src/demos/day-20.ts` — клиент/демо.
- Команды: `pnpm --filter challenge start -- day-20-server` (поднять),
  `pnpm --filter challenge start -- day-20` (брифинг), `... seed-vault` (опционально).

## Feature: «Изобрази автора» (/изобрази) — вторая игра бота «Фактчемпик»

**Задание (решение владельца):** вторая игра для бота — «Изобрази автора».
Бот выбирает настоящую цитату автора, чат 3 минуты сдаёт пародии его манеры
реплаями на анонс (каждая принятая запись тут же удаляется ботом — аноним),
затем голосование 90 с: 3 пародии + настоящая цитата вперемешку, у каждого
варианта правдоподобная дата (у настоящей — истинная). Ревил раскрывает,
где настоящая и кто автор какой пародии. Существующая /игра («кто это
сказал») остаётся без изменений; счёт сессии у игр общий.

**Правила и механика:**
- `/изобрази <имя> [тема]` — имя резолвится существующим резолвером (алиасы,
  дизамбиг-кнопки 60 с). Тема задана → настоящая цитата берётся по теме
  (FTS-путь /сказал); без темы — из игрового пула автора (40–400 зн.,
  реакции ≥5→3, без ссылок — новый `randomAuthorGameQuote`).
- Набор 3:00, в дело идут первые 3 записи (минимум 2), одна на человека,
  свою можно перезаписать. Раннее закрытие при 3/3, но не раньше 45 с
  (MIN_WINDOW; до этого анонс показывает «Принято: 3/3 — стартую…»).
- Отказы (запись не удаляется и не считается): >300 знаков; копипаст
  настоящей (нормализация + подстрока + ≥80% токенов — гард O(1), настоящая
  зафиксирована на старте раунда); дубль уже принятого текста.
- Принятая запись удаляется немедленно → анонимность до ревила. Не смог
  скрыть (бот не админ) → раунд отменяется с честным сообщением про права
  администратора. Фолбэка «в личку» нет.
- Голосование кнопками 1–4 (`vote:<token8>:<idx>`): голос за свой вариант
  отклоняется (мэпинг вариант→автор знает только бот), переголос — последнее

## Fix #51 — `pnpm --filter web build` на Windows: standalone только вне win32
**Дата:** 2026-10-24. Профиль «Поиск бага» (AGENTS §13), issue #51 (bug P3).

**Симптом:** на Windows `next build` проходил compile, manifest'ы и prerender
всех страниц, но падал на этапе 'Collecting build traces' с `EPERM` при
создании symlink react → `.next/standalone/node_modules/react`: без Developer
Mode создание symlink на Windows запрещено. Это ограничение окружения, не кода
(отмечалось ещё в ADVANCED Day 1 и Дне 5); падала только трассировка
standalone-артефакта.

**Решение:** standalone нужен только prod-деплою на Linux
(`docs/HERMES-DEPLOY-RUNBOOK.md`), поэтому в `web/next.config.ts` он включается
только при `process.platform !== 'win32'` либо явно: `NEXT_STANDALONE=1`
(форс-флаг для CI/Linux: включает standalone-вывод, но прав на symlink на
Windows не добавляет — без Developer Mode/админа сборка упадёт той же EPERM). Обычный build
достаточен для `next start`/дев-смоков — start standalone-артефакт не требует.
`postbuild` в `web/package.json` (копия `.next/static` в standalone) выполняется
только когда `.next/standalone` существует — иначе на Windows он падал бы
следом с ENOENT. Поведение Linux-деплоя не изменилось.

**Проверки:** на этой Windows-машине `pnpm --filter web build` — код 0
(48 страниц), `pnpm --filter web typecheck` и `pnpm --filter web test` — зелёные.

**Код:** `web/next.config.ts`, `web/package.json` (guard postbuild).

## Fix #103 — inbound rate-limit: per-hook бюджеты + глобальный кап только для перебора id
**Дата:** 2026-10-24. Issue #103 (security P1); ревизия по Val103CR/Val103SA2.

**Что сделано:**
- Счётчик неудач приёма `POST /api/integrations/inbound/[id]` был один на процесс:
  30 неудач против хука #1 отдавали `429` хуку #2 (cross-hook DoS 30 запросами/5 мин),
  а «сброс успехом» сам блокировался. Вечного lockout'а не было и раньше — fixed-window
  сбрасывается по времени; дыра была именно в отсутствии изоляции хуков.
- Per-hook бюджеты: `Map<hookId, {fails, resetAt}>` в `globalThis` (переживает HMR),
  30 неудач хука → `429` + `Retry-After` до конца окна (5 мин). К хуку относятся 401/400
  (включая fail `handleInboundEvent`) и 404 несуществующего id; 413/обрыв тела счётчики
  не двигают (как и было). Успешная подпись сбрасывает бюджет только своего хука.
- Глобальный abuse-guard поднят 30 → 200/5 мин и скоуплен до перебора id (Val103CR):
  гейт — только для невалидного id (до чтения тела) и неизвестного хука (после `getHook`);
  неудачи известного хука глобальный счётчик не наполняют и им не блокируются — мусор
  по чужим id не отзывается `429` на легитимные подписанные доставки.
- Карта бюджетов капится 1000 записями: истёкшие окна вычищаются; при полной карте живых
  бюджетов новый id остаётся без учёта (skip tracking), чужие живые бюджеты не вытесняются.
- Документация: `docs/AUTHORIZATION.md` — двухуровневая схема + accepted-risk F2.

**Риски/ограничения:** accepted-risk F2 — адресный lockout конкретного хука (30 мусорных
подписей/5 мин) возможен: это цена любого per-key rate-limit; митигации — мониторинг `429`,
ротация/DELETE хука. Состояние in-memory per-process (сброс рестартом, не per-IP) — как у
логина, сознательно. Skip-tracking достижим только при ~1000 живых бюджетов/окно — перебор
id раньше закрывает глобальный кап 200.

**Проверки:** `inbound-webhooks-route.spec.ts` — 25 тестов (было 22; новые: изоляция
хуков + доставка в #6 → 200 при #5 в 429; глобальный кап — 200 невалидных id → перебор
429 при проходящей доставке в известный хук; skip-tracking карты; усилены тесты окна
и сброса успехом); `pnpm --filter web typecheck` чисто; validation — Val103SA2 PASS
(док-блокер закрыт этой записью).

**Код:** `web/app/api/integrations/inbound/[id]/route.ts`,
`web/test/unit/inbound-webhooks-route.spec.ts`, `docs/AUTHORIZATION.md`.

## Fix #97 — inbound replay: опциональный x-artel-timestamp (±300 с) + зафиксированные решения
**Дата:** 2026-10-24. Issue #97 (security P3); Val97SA PASS.

**Что сделано:**
- Оценка replay-риска: подпись `x-artel-signature` покрывает только тело —
  перехваченную валидную доставку можно повторить, дедупа по id события нет.
  Для текущей модели угроз (отправители — внутренние сервисы + ручной curl,
  bind loopback, HMAC + rate-limit #103) повтор принят как осознанный риск;
  зафиксирован в `docs/AUTHORIZATION.md` (inbound-раздел).
- Опциональный `x-artel-timestamp` (Unix ms): нет заголовка — прежнее поведение
  (контракт подписи не менялся, отправители не ломаются); есть — принимается
  только при `|now − ts| ≤ 300 с`, иначе 400 «stale/invalid timestamp». Гейт
  после успешного HMAC (не oracle) и до мутации; провал двигает per-hook бюджет —
  массовый повтор захваченной доставки (старый ts в повторе) уходит в 429.
- Граница механизма (осознанно): это дедуп наивного повтора байт (ретрай,
  переигрывание из очереди/лога), а НЕ защита от активного MITM — ts не входит
  в подпись, повторщик может подменить его или просто снять заголовок. Для
  loopback достаточно; при выносе наружу — nonce с хранилищем или подпись
  заголовков (новый контракт, отдельное решение).
- Решение по 404-vs-401 oracle (#92) зафиксировано: 404 «hook not found» vs
  401 «invalid signature» — различение сохраняется (диагностика для интегратора),
  перебор id гасится лимитами, схлопывание 404→401 перебор бы не остановило.
- Документация: `docs/AUTHORIZATION.md` — replay-абзац, oracle-решение,
  рекомендации отправителям (ставить ts один раз при отправке).

**Риски/ограничения:** см. границу механизма выше; рассинхрон часов отправителя
>±300 с даёт 400 и выжигает per-hook бюджет (429 после 30 фейлов) — мониторинг
`429` на inbound-пути.

**Проверки:** `pnpm --filter web test` — 452 теста passed, включая 7 новых
(no-header → 200; fresh → 200; stale/future/garbage → 400 без мутации; bad sig +
мусорный ts → 401; массовый повтор → 429); `pnpm --filter web typecheck` чисто;
validation — Val97SA PASS.

**Код:** `web/app/api/integrations/inbound/[id]/route.ts`,
`web/test/unit/inbound-webhooks-route.spec.ts`, `docs/AUTHORIZATION.md`.

## Android: чат — MVP-паритет web /chat (2026-10-26)
**Дата:** 2026-10-26. Профиль «Бизнес-фича» (loop-run), milestone
run-2026-10-26, стори #137 эпика #134 (паритет web↔app).

**Задание:** функциональный блок «Чат» в приложении «Артель»: те же сессии, что
на web `/chat` — список, создание с выбором стратегии памяти и системного
промпта, переписка с живым SSE-стримингом, остановка генерации, сброс
истории. Скоуп MVP не включает `joker/antonov`, панели
memory/branch/profile/constraints — они остаются в backlog эпика.

**Что сделано:**
- Чистый SSE-парсер `data/api/ChatStream.kt`: безымянные события
  `data: <JSON>` через `\n\n` (контракт web `web/lib/shared/sse.ts`:

  закрытие соединения, `[DONE]`-сентинела нет). Session-feed API

- Репозиторий: `chatSessions`, `createChatSession`, `chatSession`,
  `resetChatSession` (Retrofit) и `chatStream` — OkHttp напрямую
  (readTimeout 0, connect 15 c, Bearer как в остальных запросах; 401

  Отмена стрима (`cancelChatStream`) — кнопка «Остановить»; okhttp call
  cancel не роняет UI: partial текст остаётся в пузыре.
- Экраны: `ChatsScreen` (список сессий + диалог создания: стратегия
  full/sliding/sticky/branching, системный промпт ≤2000) и `ChatScreen`

  стрим-текстом, стоп, сброс с подтверждением, счётчик токенов в шапке).
  Вход: карточка «Чат» на дашборде + маршруты `chat` / `chat/{sessionId}`.
- Тесты: `ChatStreamTest` (5 кейсов парсера: последовательность,
  чанки-дописывание, битый JSON, неизвестные события, пробелы после
